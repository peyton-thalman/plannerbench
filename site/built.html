Case study

A financial advisor, AI as the team, and a rule: build the judge first

I’m a licensed financial advisor, not a software engineer. Over eight days in October 2026 I directed AI coding agents to build a planning engine, a benchmark that proves models need it, the tools that hand it to them, and a demo that puts it in a client meeting. This page is how the decisions got made.

The problem

“Is AI smart?” is the wrong question

  • The real question. Which planning questions can an advisor trust a model with on its own, and which need verified math behind it? Nobody could answer that with evidence.
  • Why it matters. In this field a confident wrong number costs a family real money: a Roth conversion sized wrong here gave up $26,002. And a firm’s compliance team has to be able to defend every number a tool shows.
  • Who it’s for. Wealth-tech product teams deciding what to build, compliance teams deciding what to allow, AI labs looking for hard, current, exact questions, and advisors asking “can I check this with AI?”
  • The bet. Models are good at language and judgment, and unreliable at rules that change every year. So put the rules in tested code, and let the model choose the inputs and explain the result.

How I work

Six principles, each with where it paid off

01

Build the judge before the feature

Every piece started with the check that would prove it right: answer keys before questions, graders before models, fake meetings with answer keys before the meeting app.

The Gauntlet’s grader passed 12 stand-in checks, including a fake model that answers perfectly and one that lies, before a single real model was asked.

02

The published source decides

When the models and the key disagree, the IRS form, SSA’s manual or the CMS table settles it. Never a vote among models.

Four different models from three labs gave the same senior-deduction answer. Schedule 1-A Part V showed all four were wrong.

03

Never let the builder grade itself

A second engine was written from the written spec alone, by an AI agent that was never allowed to read the first one.

Its first run found 3 differences in 2,000 households. One was a real bug in the main engine (a 2027 tax threshold). Now 4,000 of 4,000 agree.

04

Spend in capped steps

A smoke test under $1, then a small run under $5, then a decision. Every run has a hard spending cap.

One run overshot its $5 cap by $0.39 because requests already in flight weren’t counted. The cap now reserves each request’s worst case.

05

Hold out what you tune on

Private questions from a secret seed are never published and never used to improve anything. They exist only to check that an improvement is real.

The tool redesign was built on public questions, then scored 48 of 50 on held-out questions it had never seen.

06

Cut scope on purpose

Speed comes from saying no. Once the engine proved to be the valuable part, the demo app’s features were frozen.

About 18 of 23 demo commits had gone to polish anyone could build. The next week went to the engine and the proof instead.

Timeline

Eight days, four stages

Each stage ended with a measured result before the next one started.

  1. Oct 15

    The engine

    A planning engine for federal tax, Social Security, RMDs and Medicare premiums, red-teamed the same day for rule errors.

  2. Oct 20

    The benchmark and the demo

    2,800 public and 700 held-out questions; PolicyEngine as an outside check (1,600 of 1,600 agree); seven model setups from five labs. The same day: the Wizard demo, built behind its own grader.

  3. Oct 21

    The fix, and the proof

    The engine as MCP tools. Version 1.0 got overruled; 1.1 showed its rule and went 50 for 50. The clean-room second engine and a year-by-year scenario runner for 25-year plans.

  4. Oct 22

    The Gauntlet

    A Roth-conversion solver, 110 whole-household decisions built so no shortcut works, a grader that tracks every time a model overrules the engine, and the first results: 22 of 22 with the engine.

What’s next

Ranked, with the reason for each

Ordered by what most raises trust in the result per dollar spent.

  1. Run the full Gauntlet, including the 33 held-out questions. Today’s gap rests on 11 questions with wide intervals. All 77 public questions turn “a clear gap” into a result (about $127 for three Claude models, so it waits for a go-ahead), and the 33 held-out ones then show it isn’t tuned.
  2. A CPA signs off on the answer key. Two engines and PolicyEngine agree, but a licensed outside reviewer is what a firm’s compliance team will ask for first. It costs time, not money.
  3. Other labs’ models on the Gauntlet. The fix is a tool design, not a Claude trick. Showing it works for other labs’ models proves that.
  4. Gauntlet v2: ask before advising. Real clients leave facts out. The next test is whether a model asks for the missing fact instead of guessing. It comes after the three above because it needs a trusted v1 to compare against.
  5. Harder compliance questions. Today’s define the issue in the question, so every model scores 91–100%. Useful, but it tests reading, not knowledge.

The demo

Wizard: where the engine meets a meeting

  • What it does. As an advisor and a client talk, the intake form fills itself in. When someone asks a planning question out loud (“what if we converted some of Dana’s IRA?”), the engine’s answer appears as a card a few seconds later, in plain English, with every fact it used and where that fact came from.
  • Graded like everything else. It was built against fake meetings with answer keys, up to an hour long, with hedges, corrections and spouses who disagree.
  • Safe by design. Fake households only. Sensitive numbers are masked in the browser before any model sees them, and speech can be transcribed on the laptop so no audio leaves it.
  • Frozen on purpose. It’s the demo. The engine and the proof are the product.
